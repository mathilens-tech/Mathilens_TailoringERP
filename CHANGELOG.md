## [Unreleased]

### Added

- Orders export: the Orders list now downloads its current status and free-text filter as an Excel spreadsheet or PDF. The dedicated `ExportOrdersQuery` is bounded to 5,000 rows without weakening the normal list endpoint's 100-row pagination limit, and batches payment lookup for the entire file rather than issuing one billing query per order. Exports contain the order number, lifecycle dates/status, order value, paid/balance amounts, garment lines, and notes. One new handler test; 502 unit tests passing.
- Initial repository structure (docs, prompts, src, tests, scripts, assets, docker, CI workflows) prepared for enterprise product development.
- Solution scaffolding: Clean Architecture .NET solution (`MathilensERP.Domain`, `.Application`, `.Infrastructure`, `.Api`, `.Shared`, `.UnitTests`, `.IntegrationTests`) with project references enforcing the documented dependency rules ([01_ARCHITECTURE.md § 6](docs/01_ARCHITECTURE.md#6-dependency-diagram)). Swagger via Swashbuckle per the documented API standard.
- Shared kernel (`MathilensERP.Shared`): `Result`/`Result<T>` and `Error`/`FieldError` types for modeling expected business outcomes without exceptions, `Guard` clauses for Domain invariant enforcement, and `PaginationDefaults` constants — with unit test coverage.
- Domain base entity (`MathilensERP.Domain.Common.AuditableEntity`): standard audit footprint (created/modified/deleted by+when) and soft delete, per 02_DATABASE.md §§ 5-6. Concurrency is deliberately handled at the Infrastructure/EF Core level (PostgreSQL `xmin`), not in Domain.
- Database foundation: EF Core `ApplicationDbContext` targeting PostgreSQL exclusively (`Npgsql.EntityFrameworkCore.PostgreSQL`), ASP.NET Core Identity (`ApplicationUser`/`ApplicationRole`) extended with the standard audit/soft-delete footprint, a `RefreshToken` domain entity for JWT rotation, a centralized soft-delete global query filter and audit-stamping `SaveChanges` interceptor, and the `InitialCreate` Code First migration. Identity's default `AspNetXxx` tables renamed to match 02_DATABASE.md's naming standard (`Users`, `Roles`, `UserRoles`, `UserClaims`, `UserLogins`, `UserTokens`, `RoleClaims`, `RefreshTokens`). 34 unit tests passing.
- Application layer foundation: a small hand-rolled in-process mediator (`ISender`, `ICommand`/`IQuery`, `IPipelineBehavior`) implementing 01_ARCHITECTURE.md § 25.3 without a third-party dependency, plus a FluentValidation-backed `ValidationBehavior` implementing § 11 Validation Strategy. `AddApplication()` registers handlers/validators via assembly scanning, per 00_MASTER_SPEC.md § 16.2.
- Authentication use cases: `LoginCommand` and `RefreshAccessTokenCommand` (Application) with validators, dispatched through `IIdentityService` (a port kept free of ASP.NET Core Identity's concrete types) implemented by `IdentityService` (Infrastructure) — JWT access token issuance, opaque refresh tokens (only the hash persisted), single-use rotation, and replay detection that revokes all of a user's active tokens, per 00_MASTER_SPEC.md § 10.1 / 01_ARCHITECTURE.md § 17. 51 unit tests passing.
- Api layer: `AuthController` (`POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`) and a protected `GET /api/v1/users/me` proving JWT bearer enforcement; `ApiControllerBase` maps `Result`/`Result<T>` to the standard success/error envelope (00_MASTER_SPEC.md § 8.6-8.7) including `ErrorType` → HTTP status mapping; `GlobalExceptionHandler` (§ 13 Exception Strategy) ensures no unhandled exception ever reaches a client as a raw stack trace; JWT bearer authentication middleware, Swagger with a bearer-token security definition, and XML doc comments surfaced in Swagger UI. Verified end-to-end via a local smoke test and 5 new `WebApplicationFactory`-based integration tests covering the paths that don't require a live database (validation failures, missing/malformed bearer tokens) — all passing. 56 tests passing total.
- Next.js dashboard shell (`web/`): login page against the auth API, a JWT-backed authenticated dashboard shell with sign-out and a dark/light theme toggle, and a thin fetch client matching the API's response envelope. CORS wired on the Api for the frontend's configured origin.
- GitHub Actions CI (`.github/workflows/ci.yml`): parallel `.NET build & test` and `Frontend lint & build` jobs on every push/PR to `main`.
- Customer Management backend (Phase 2's first module, 02_DATABASE.md § 10.3): `Customer` domain entity (`Domain/Customers`) enforcing full name + phone number as required invariants; EF Core configuration, `AddCustomers` migration, and a `CustomerRepository` (`Infrastructure/Persistence/Customers`) implementing the `ICustomerRepository` port (01_ARCHITECTURE.md § 25.1 Repository Pattern) with `SaveChangesAsync` exposed directly on it per § 25.7 (no separate Unit of Work abstraction). Application layer: `CreateCustomerCommand`, `UpdateCustomerCommand`, `DeleteCustomerCommand` (soft delete), `GetCustomerByIdQuery`, and a paginated `SearchCustomersQuery` (free-text over name/phone, using PostgreSQL's `ILIKE` via `EF.Functions.ILike`) — all with FluentValidation validators. A new `PagedResult<T>` (Shared) and `PaginationMeta`/`ToPagedActionResult` (Api) generalize the § 8.3 pagination envelope for future list endpoints. `CustomersController` (`/api/v1/customers`, `[Authorize]`-protected) exposes Create/GetById/Search/Update/Delete. 28 new unit tests (entity invariants, handlers, validators) plus 7 new integration tests (auth-gate and validation-error paths, following the same no-live-database-yet pattern as the Auth module's integration tests) — 91 tests passing total.
- Measurement Management backend (Phase 2's second module, 02_DATABASE.md §§ 10.4-10.5): `Measurement` (the current, active set for a customer + garment type) and `MeasurementHistory` (immutable snapshots, `IAuditable` directly rather than `AuditableEntity` — not soft-deletable, matching RefreshToken's precedent) domain entities in `Domain/Measurements`, plus a `GarmentType` enum (Shirt, Trousers, Suit, Blazer, Kurta, Blouse, Dress, Other). **Design decision**: measurement points are a flexible name/value set (`IReadOnlyDictionary<string, decimal>`, persisted as an ordinary JSON-text column, not a provider-specific JSON column type) rather than fixed per-garment-type properties — 02_DATABASE.md § 10.4 Future Expansion explicitly scopes "garment-type-specific measurement templates" as future work, so hardcoding columns per garment now would be exactly the speculative complexity YAGNI (00_MASTER_SPEC.md § 4.5) rules out; values are assumed centimeters by shop convention pending a real unit requirement. `AddMeasurements` migration; `MeasurementRepository` implementing `IMeasurementRepository`. Application layer: `CreateMeasurementCommand` (404 if the customer doesn't exist, 409 if a measurement for that customer+garment type already exists), `UpdateMeasurementValuesCommand` (snapshots the pre-update values into `MeasurementHistory` before applying the change), `GetMeasurementByIdQuery`, `GetMeasurementsByCustomerQuery` (unpaginated — bounded by the small, fixed `GarmentType` set), and a paginated `GetMeasurementHistoryQuery`. `MeasurementsController` (`[Authorize]`-protected; customer-nested routes for create/list, flat routes for by-id/update/history) exposes all five. 34 new unit tests plus 5 new integration tests — 125 tests passing total.
- Employee Management backend (Phase 2's third module, 02_DATABASE.md § 10.6): `Employee` domain entity (`Domain/Employees`) with full name required, job title/phone/email optional, and a nullable `UserId` reserved for the documented optional one-to-one link to a system login. That link is schema-only for now — `EmployeeConfiguration` wires a real FK to `ApplicationUser` plus a filtered unique index (`WHERE "UserId" IS NOT NULL`) so the constraint exists in the database, but no command in this module sets `UserId` yet, since linking an employee to a login account is the same admin/role-management flow Phase 1 already deferred pending a live database. `AddEmployees` migration; `EmployeeRepository`. Application layer mirrors Customer Management: `CreateEmployeeCommand`, `UpdateEmployeeCommand`, `DeleteEmployeeCommand` (soft delete), `GetEmployeeByIdQuery`, paginated `SearchEmployeesQuery`. `EmployeesController` (`/api/v1/employees`, `[Authorize]`-protected). 22 new unit tests plus 5 new integration tests — 156 tests passing total.
- Tailoring Orders + Fabric Details backend (Phase 2's fourth and fifth modules, built together, 02_DATABASE.md §§ 10.7-10.8, 10.11): `Order` is the aggregate root — `Domain/Orders` — owning a collection of `OrderItem`s (each with an optional one-to-one `FabricDetails`), all only ever created/modified through `Order`'s own public methods (`AddItem`, `SetItemFabric`, `AssignEmployee`, `TransitionTo`), never independently; both child types have `internal` factory methods enforcing that. **Design decision — order lifecycle**: a strict, enforced state machine per 02_DATABASE.md § 10.7's own example ("cannot move to Delivered without passing through In Progress") — `Received → InProgress → ReadyForDelivery → Delivered`, with cancellation allowed from any non-terminal state, both terminal. Every mutating command checks `Order.CanTransitionTo`/`CanModifyItems` *before* calling the mutating method, converting an invalid attempt into a clean `409 Conflict` rather than an unhandled exception (01_ARCHITECTURE.md § 13). `AddOrders` migration, including real FKs from `Orders` to `Customers`/`Employees` and cascade-owned `OrderItems`/`FabricDetails`; `OrderRepository` (always eager-loads the full aggregate). Application layer: `CreateOrderCommand` (creates an order with its initial items/fabric in one call — validates the customer and, if provided, the assigned employee both exist), `AddOrderItemCommand`, `SetOrderItemFabricCommand`, `TransitionOrderStatusCommand`, `AssignOrderEmployeeCommand`, `GetOrderByIdQuery`, and a paginated, customer/status-filterable `SearchOrdersQuery`. `OrdersController` (`/api/v1/orders`, `[Authorize]`-protected) exposes all of it. 41 new unit tests plus 6 new integration tests — 210 tests passing total. **This completes Phase 2's backend** (Customer, Measurement, Employee, Orders/Fabric Details).
- Billing backend (Phase 3's first module, 02_DATABASE.md §§ 10.9-10.10): `Invoice` is the aggregate root — `Domain/Billing` — owning a collection of `Payment`s (`IAuditable` directly, not `AuditableEntity`, matching `MeasurementHistory`/`RefreshToken`'s precedent for insert-only, never-edited records), only ever created through `Invoice.RecordPayment`. **Design decision — Order relationship**: kept 02_DATABASE.md § 10.9's stated default (many-to-one: an order may accumulate more than one invoice over time, each invoice bills exactly one order) rather than building many-to-one-spanning-multiple-orders, which the doc explicitly frames as this module's decision to make, not a requirement. **Design decision — status**: `Unpaid → PartiallyPaid → Paid`, or `Void`, recomputed automatically by `RecordPayment` from `AmountPaid` vs. `TotalAmount` — never set directly, so it can't drift from the payment history. Voiding is only allowed on an invoice with zero payments recorded (`CanVoid`); a partially/fully paid invoice needs a documented credit/adjustment process that isn't built yet (02_DATABASE.md § 10.9's "not an in-place edit of a settled invoice" — scoped out of V1, noted as a gap below). `AddBilling` migration, with real FKs from `Invoices` to `Orders`/`Customers`; `InvoiceRepository`. Application layer: `CreateInvoiceCommand` (computes `Subtotal` from the order's items, validates the order exists and has items, and that the discount doesn't zero out or exceed the total), `RecordPaymentCommand`, `VoidInvoiceCommand`, `GetInvoiceByIdQuery`, and a paginated, customer/status-filterable `SearchInvoicesQuery`. `InvoicesController` (`/api/v1/invoices`, `[Authorize]`-protected). Invoicing is a deliberate, explicit staff (or future automation) action rather than an automatic side effect of an order reaching `Delivered` — there's no domain-event dispatch mechanism wired up yet (01_ARCHITECTURE.md § 26 Future Event-Driven Architecture is exactly that, future). 40 new unit tests plus 6 new integration tests — 250 tests passing total.

- WhatsApp backend (Phase 3's second module, 00_MASTER_SPEC.md § 3 / § 5): `WhatsAppMessage` (`Domain/WhatsApp`) is a persisted log entry per send attempt — `Pending` at creation, then `Sent`/`Failed` — for auditability and delivery-status tracking (01_ARCHITECTURE.md § 11.5: "failures are logged and surfaced"). **Provider choice**: Meta's WhatsApp Cloud API, called directly (the user's explicit decision over Twilio), behind an `IWhatsAppSender` port (`Application/Common/Interfaces`) so the product isn't locked to that specific provider (01_ARCHITECTURE.md § 28 Risks). `MetaWhatsAppSender` (`Infrastructure/WhatsApp`) is a typed `HttpClient` matching Meta's documented `POST /{api-version}/{phone-number-id}/messages` contract — **unverified against a live account**: no real Meta Business/WhatsApp Business Account credentials have been available in this environment, so it has never actually sent a message. `WhatsAppOptions` is deliberately *not* required-on-start (unlike `JwtOptions`) — the API must start cleanly without WhatsApp configured, and `MetaWhatsAppSender` returns a graceful `Failed` result per-send when credentials are missing, rather than throwing. `AddWhatsAppMessages` migration, with real FKs to `Customers`/`Orders` (the latter nullable — not every message is order-related). Application layer: `SendWhatsAppMessageCommand` (persists the message as `Pending` in its own commit, calls the sender, then commits the final status in a second commit — deliberately two transactions, not one spanning the external HTTP call), `GetWhatsAppMessageByIdQuery`, and a paginated, customer/order/status-filterable `SearchWhatsAppMessagesQuery`. `WhatsAppMessagesController` (`/api/v1/whatsapp-messages`, `[Authorize]`-protected). Sending is an explicit action, same as Billing's invoicing, for the same domain-event-dispatch-doesn't-exist-yet reason (01_ARCHITECTURE.md § 26 describes it as already active — "Now:" — but no code in this project actually implements it; this is a pre-existing gap this module doesn't retrofit). 24 new unit tests plus 5 new integration tests — 274 tests passing total. Per this codebase's established precedent (repositories are never unit-tested directly, only through their ports via mocked interfaces), `MetaWhatsAppSender` itself has no direct unit test either — only `IWhatsAppSender` consumers do.

- Settings backend (Phase 3's third module, 02_DATABASE.md § 10.12): `Setting` (`Domain/Settings`) is a simple key-value entity — `IAuditable` directly, not `AuditableEntity`, since § 10.12's own Retention Rules explicitly exempt Settings from the standard soft-delete pattern ("configuration is either present with a current value, or genuinely removed... never 'soft' in between"). Keyed by `Key`, its natural identifier — no other entity references a `Setting` by foreign key, matching the doc's own description ("referenced by nearly every module for configuration values rather than holding foreign keys itself"). `AddSettings` migration with a unique index on `Key`; `SettingRepository`. Application layer: `UpsertSettingCommand` (creates if the key doesn't exist, updates the value if it does — the natural single operation for a key-value store, rather than forcing an artificial create/update split), `DeleteSettingCommand`, `GetSettingByKeyQuery`, and a paginated `ListSettingsQuery`. `SettingsController` (`PUT/GET/DELETE /api/v1/settings/{key}`, `GET /api/v1/settings`, `[Authorize]`-protected). 16 new tests — 295 tests passing total.

- Reports backend (Phase 3's fourth and final module, 01_ARCHITECTURE.md § 20 Reporting Strategy): no new Domain entity or migration — reports are pure read-side projections over `Orders`/`Invoices` ("project directly from persistence... bypassing full entity materialization"), so `IReportRepository`/`ReportRepository` (`Application`/`Infrastructure`) is the entire module, computing aggregates via direct LINQ (`GroupBy`/`Sum`/`Count`) rather than materializing full aggregates. Three reports, a reasonable MVP scope given 00_MASTER_SPEC.md/prompts/10_REPORTS.md don't enumerate specific ones: **revenue** (total invoiced/collected/outstanding for a date range), **order-status-summary** (order counts per `OrderStatus` for a date range — every status is present in the result even at zero, so consumers never have to treat "absent" and "zero" as different cases), and **outstanding-invoices** (unpaid/partially-paid invoices, oldest first, paginated). `GetRevenueReportQuery`, `GetOrderStatusSummaryReportQuery`, `GetOutstandingInvoicesReportQuery`. `ReportsController` (`/api/v1/reports/*`, `[Authorize]`-protected). 22 new tests — 312 tests passing total. **This completes Phase 3's backend** (Billing, WhatsApp, Settings, Reports) — and with it, every module in Phase 2 and Phase 3's charter.
- Customer Management frontend (`web/`) — the first module frontend beyond Phase 1's dashboard shell: a customers list page (`/dashboard/customers`) with debounced server-side search (00_MASTER_SPEC.md § 9.7 — never a client-side filter over an unbounded list), paginated table, and a blocking delete confirmation (§ 9.5/9.11); create (`/new`) and edit (`/[id]`) pages sharing a `CustomerForm` component that preserves entered input and shows field-level errors on validation failure (§ 9.5 Forms), mapped from the API's error envelope the same way the Phase 1 login page already does. Introduces the start of the shared component library § 9.4 calls for (`components/ui/`): `Button`, `Input`/`Textarea`, `Pagination`, `ConfirmDialog`, and a `ToastProvider` for non-blocking success/error notifications (§ 9.11), now wired into the root layout. Extended `api-client.ts` with `apiPut`/`apiDelete` and a paginated `apiGetPaged` that surfaces `meta` (previously discarded). Verified in a headless browser against the (expectedly) unreachable local API: list/edit pages show a graceful error state rather than crashing, the create form shows a friendly error and preserves what was typed, and navigation all works — this proves the frontend's own logic, not a real round trip to a live backend (see Known Gaps).

- Fix: enums now serialize as strings over JSON, not raw integers. Every enum in this API's contracts (`OrderStatus`, `InvoiceStatus`, `GarmentType`, `PaymentMethod`, `FabricSource`, `WhatsAppMessageType`, `WhatsAppMessageStatus`) was serializing as its underlying `int` by System.Text.Json's default, since no `JsonStringEnumConverter` had been registered — fragile for API consumers and undocumented in Swagger. Discovered while building the Measurement Management frontend, which needs to send/receive readable `GarmentType` values. Query-string enum params (e.g. `?status=Received`) were already unaffected, since `[FromQuery]` binding doesn't go through `System.Text.Json` — only request/response body fields were broken. Added an integration test proving the fix rather than just confirming nothing regressed: a fully-valid request with a string `GarmentType` now passes model binding and validation, reaching the handler (evidenced by a 500 from the expected-unreachable database, not a 400 from a binding failure).
- Measurement Management frontend: a `MeasurementsSection` embedded in the customer detail page (never a standalone top-level list — measurements are always accessed through their owning customer) with a free-form `MeasurementValuesEditor` (add/remove name-value point rows) shared between create and edit, and a standalone paginated measurement-history page. `lib/api/measurements.ts` adds the typed API client.

Adds two new shared components: `SearchPicker` (`components/ui/`), a debounced server-side search dropdown for picking a related record (customer, employee) — generic over item type, reusable for any future "pick a related record" need; and `OrderItemsEditor` (`components/orders/`), a dynamic garment-line editor where each line optionally carries its own fabric details, used on the create-order form. The order detail page computes valid next statuses client-side from the same state machine the backend enforces (`Received → InProgress → ReadyForDelivery → Delivered`, cancellable from any non-terminal state) to render only the transitions that are actually legal, and supports employee (re)assignment, adding items, and setting per-item fabric — all inline on the same page, no separate routes, mirroring how the equivalent backend actions are all sub-resources of one order. Verified in-browser: list/detail graceful error states, nav link, and client-side validation (e.g. submitting without a selected customer) all work.
- Billing frontend: a "Create Invoice" action lives on the order detail page (not a standalone "new invoice" route) since invoicing is order-initiated on the backend too; a standalone invoices list with a status filter; and a detail page with a record-payment form and a void action, gated client-side by the same rule the backend enforces (`amountPaid === 0`), backed by the existing `ConfirmDialog`. Fixed a real bug caught before it shipped: `voidInvoice` initially called the generic `apiPost<T>` helper, which tries to parse a JSON response body — but the `Void` endpoint returns `204 No Content` on success, so that call would have thrown trying to parse an empty body. Added `apiPostNoContent` (`api-client.ts`) mirroring the existing `apiDelete` pattern for exactly this shape of endpoint (an action, not a resource creation), and used it instead.

Verified in-browser: list/detail graceful error states, nav link, client-side validation (submitting without a selected customer).

No separate routes, matching how small this module's surface is. Verified in-browser: graceful error state, nav link, form preserving input on failure.

- Reports frontend (the eighth and final module frontend): a single `/dashboard/reports` page — a shared From/To date range drives the Revenue summary (numeric tiles: invoice count, invoiced/collected/outstanding totals) and the Order Status Summary table (count per `OrderStatus`), fetched together since both reports share the same date range; a separately paginated Outstanding Invoices table underneath needs no date range, matching the backend's own oldest-first default. Deliberately kept to plain numeric tiles and tables, no charting library, given how large this session's scope already was. **This completes every module frontend across Phase 2 and Phase 3** (Customer, Measurement, Employee, Orders/Fabric Details, Billing, WhatsApp, Settings, Reports). Verified in-browser: nav link, both graceful error states (summaries and outstanding invoices independently), date inputs.

- **First live-database verification of this project.** A real PostgreSQL 18 instance (Azure Database for PostgreSQL Flexible Server) became available for the first time this session. All 8 migrations (`InitialCreate` through `AddSettings`) applied cleanly with `dotnet ef database update` — the EF Core model's relationships, conversions, and indexes round-tripped against real PostgreSQL for the first time, resolving the single biggest risk flagged repeatedly throughout Phase 1-3. The connection string is stored via `dotnet user-secrets` (`src/Api`, `UserSecretsId` added to the `.csproj`), never in a committed `appsettings.*.json` — the existing `Password=postgres` local default in `appsettings.Development.json` stays as a harmless placeholder for anyone without a configured secret. Verified end-to-end: (1) via the API directly — login, create customer, get-by-id, and paginated search all round-tripped correctly; (2) via the browser against the running frontend — real login (not a fake localStorage token, unlike every prior smoke test this session), customer creation, and adding a measurement through `MeasurementsSection`, which had never rendered against live data before — zero console errors. Test records created during verification were deleted afterward. **Gap surfaced by this work**: there is still no user registration/admin-bootstrap endpoint anywhere in the API — the only way to create a login today is directly via `UserManager<ApplicationUser>` in a one-off script, not through any HTTP endpoint. A `/api/v1/auth/register` (or an admin-only user-management flow) is now a concrete piece of missing Phase 2 scope, not just a deferred nice-to-have.

- Delivery is now gated on payment, and records when it happened. `Orders` gains a nullable `DeliveredAtUtc` (`AddOrderDeliveredAt` migration), set by `Order.TransitionTo` only on the move to `Delivered` and required there — the date is supplied by the caller rather than stamped from the clock, so a handover entered the next morning is still dated the day it actually happened. On the frontend, "Mark as Delivered" opens a `ConfirmDialog` (now able to carry its own fields via `children`) with a date defaulted to today; every other transition still fires straight through. **Design decision — where the payment rule lives**: "no pending amount" is a billing fact, so `TransitionOrderStatusCommandHandler` checks it via a new `IInvoiceRepository.GetOutstandingAmountForOrderAsync` (summed in the database, since `Invoice.RemainingBalance` is computed and untranslatable) rather than `Order` — the order aggregate has no visibility of its invoices, and reaching across aggregates inside Domain to give it one would be worse than the coordination living in the handler. Any live (non-voided) invoice with a balance blocks delivery with a `409 Order.PaymentPending` naming the amount; an order that was never invoiced has nothing outstanding and so is still deliverable, matching the rule as stated ("any pending amount") rather than silently widening it into "must be invoiced and settled".

- Orders & Collections report, plus preset date ranges across the whole Reports page. A fourth report (`GET /api/v1/reports/order-collections`) answering the question Revenue structurally cannot: Revenue sums *invoiced* amounts, so work the shop took and never billed is invisible in it. This one values orders from their own items (quantity × unit price) and reports order count, order value, delivered value, collected, pending, cancelled value and discounts given. **Design decision — cohort by booking date**: every figure describes the same set of orders, the ones *booked* in the range, so they reconcile against each other. Keying on delivery date was considered and rejected — it would make "pending" structurally zero, since an order can no longer be delivered while any amount is outstanding on it. **Pending** is the balance on live invoices *plus* the full value of orders never invoiced, not order value minus collected: the latter goes negative on a fully-settled order whose invoice carried tax. Cancelled orders are counted for their own tile only and excluded from every other money figure. The page gains a preset bar (Today, Last 7/30 days, Last 3/6/9 months, Last 1 year, Custom) driving *all* date-scoped sections from one control, so no two sections can silently describe different periods; editing either date is itself the way into Custom. Preset dates are read off the local calendar, since "Today" has to mean the shop's today, not UTC's. **Scope note**: these are sales figures, not profit, and the UI says so — see the Known Gaps entry below for what profit would actually require.
- Fix: the last day of every report range was being excluded. The Reports page sent the To date's *midnight* as `toUtc` while the backend filters `CreatedAtUtc <= toUtc`, so anything that happened on the final day of the range fell outside it — today's figures never appeared at all, and a "Today" filter would have returned zeros every time. The range now ends at 23:59:59.999 of the To date. This shifts existing Revenue and Orders-by-Status numbers upward, correctly. Report date ranges are still interpreted as UTC days rather than the shop's local ones — a separate, unaddressed nuance for a shop running at IST.

- Fix: the API now applies pending migrations at startup in every environment except Development, closing the gap that had silently broken production. Nothing in the pipeline ever applied them — `deploy-api.yml` publishes and deploys, there was no `Migrate()` call, and the practice was to run `dotnet ef database update` by hand. That practice lapsed: production was found running with `AddClothPrices` and `AddOrderNotes` unapplied, so the deployed API had been querying an `Orders."Notes"` column and a `ClothPrices` table that did not exist in the database. Guarded on *not* Development rather than on Production specifically, so a deployed slot migrates whatever it calls itself, while the integration tests — which boot the same host through `WebApplicationFactory` with no database behind it — stay out of the path. Deliberately unguarded against failure: if migration throws, startup fails and the deploy is visibly broken, which beats serving traffic against a schema the code doesn't match. **Note**: this requires the runtime connection string's user to hold DDL rights; the account that has been applying migrations by hand is not necessarily the one the Azure Web App connects with. Worth confirming before the next schema change.
- Fix: `MeasurementsEndpointsTests.Create_WithValidStringGarmentTypeAndValues_PassesValidationAndReachesTheHandler` no longer passes or fails by accident of the machine it runs on. It asserted a 500, which only happens where nothing is listening on `localhost:5432` — true in CI, false on a developer box running PostgreSQL, where the same request reaches the handler and returns 404 for the unknown customer. Both outcomes prove the point the test exists to prove (that `"Shirt"` binds to `GarmentType`, which a 400 would disprove), so it now asserts the response is not a 400 and nothing more.

- The orders list now shows Amount, Advanced and Balance per row. `OrderDto` gains `TotalAmount` (summed from the order's own items, so it needs no invoice to exist), a nullable `AmountPaid`, and `BalanceAmount`. **Design decision — why `AmountPaid` is nullable**: `null` means "not looked up on this path", never "nothing has been paid". Only the two read paths that actually need the figure pay for it (`GetOrderByIdQueryHandler`, `SearchOrdersQueryHandler`); the eight command handlers that also return an `OrderDto` leave it null rather than issuing a billing query nobody asked for. A `0m` default would have been indistinguishable from a real zero and would have shown a full balance as outstanding on screens that never checked. The list path uses a batched `IInvoiceRepository.GetPaidAmountsForOrdersAsync` returning a dictionary keyed by order — one query per page, not one per row.

- Deleting a record that is still in use is now refused rather than silently soft-deleted. `DeleteCustomerCommandHandler` returns `409 Customer.InUse` ("Customer used in Orders.") when any order references the customer, and `DeleteEmployeeCommandHandler` returns `409 Employee.InUse` when any order has the employee assigned. Both check via a repository existence probe rather than loading the orders. Without this, a soft-deleted customer stayed invisibly attached to live orders — the order detail page would render a customer the customers list said had been removed.

- Customer records gained profile fields: `Gender` (Male/Female/Other), optional `Birthday` and `WeddingDate`, and an optional `Religion` (`AddCustomerProfileFields` migration; both enums persisted as strings via `HasConversion<string>()`, so a value added later doesn't renumber the existing rows). The customers list gained a Religion filter alongside the existing search. **Open question for the shop owner**: `Religion` is a fixed enum (Hindu, Muslim, Christian, Sikh, Jain, Buddhist, Other) rather than free text — cheap to change now, awkward once real data exists.

- The order detail page now shows the customer's previous orders, matched by phone number rather than by customer id (`GET /api/v1/orders/{id}/previous`, `GetPreviousOrdersQuery`). Matching on the phone is deliberate: the same walk-in is frequently entered twice under slightly different names, and the phone is what actually identifies them. The current order is excluded from its own history.

- Every paginated screen gained a page-size control (10/20/50/100). `Pagination` exports `PAGE_SIZE_OPTIONS` and `DEFAULT_PAGE_SIZE`, takes an optional `onPageSizeChange`, and now shows the row count even when there is only one page — previously a single-page result rendered nothing at all, so the user couldn't tell an empty page from a filtered one.

- The left navigation now collapses, on every screen size. Two pieces of state, not one: below `lg` the nav is a drawer that slides over the content with a tap-to-dismiss backdrop; at `lg` and above it is a rail that shrinks to icons. A single shared boolean would have to pick a default that is wrong on one of the two — either the drawer opens by default on a phone or the desktop rail starts collapsed. Which of the two toggle buttons is visible is decided by CSS, so neither has to guess the viewport before the first paint.

- Activity log (`Domain/Activity/ActivityLog`, `AddActivityLogs` migration) recording every successful command, with Date, User and Screen filters on `/dashboard/activity`. Written by an `ActivityLogBehavior` in the mediator pipeline rather than by each handler, so a new command is logged the day it is written and cannot be forgotten. **Design decisions**: only *successful commands* are recorded — queries would bury the actual changes in read noise, and a rejected command changed nothing. `Screen` and `Action` are derived from the command's own type by `ActivityDescriptor` (the namespace segment after `MathilensERP.Application.`; the type name minus `Command`, split on PascalCase) rather than hand-labelled at each call site, which would drift. The log is insert-only with no audit footprint and no soft delete — a tamper-evident record you can edit is not one. `UserName` is copied in at write time rather than joined at read time, so the log still reads correctly after a user is renamed or removed. A logging failure is swallowed and reported to `ILogger` rather than thrown: the command has already committed, and failing the request afterwards would tell the user their change was rejected when it was not.

- Role-based user rights (`Shared/Authorization`). Four roles — `Owner`, `Manager`, `FrontDesk`, `Tailor` — each mapping to a fixed set of permissions (`Module.View`/`Module.Manage` across Customers, Measurements, Employees, Orders, Invoices, WhatsApp, Reports, Pricing, Settings, Activity and Users). Enforced with one ASP.NET Core authorization policy per permission, generated from the catalogue at startup, applied per action on every V1 controller. **Design decision — permissions resolved per request, not baked into the token**: `PermissionAuthorizationHandler` maps the caller's *role* claim to permissions at request time, so changing someone's role takes effect on their next request instead of whenever their token happens to expire. An unrecognised role in an old token grants nothing rather than throwing. Exactly one role per user, and `UserAdminService` refuses to demote the last remaining Owner (`Users.LastOwner`) — locking every administrator out of the system is not an action worth supporting. Adds the admin screen this project has never had: `/dashboard/users` lists users with their role, creates users, and changes roles, gated on `Users.Manage`. `GET /api/v1/users/me` now returns the caller's roles *and* their resolved permissions, which drives `usePermissions()` and the nav filter — a screen the user has no permission for is not offered. That is presentation only: the server enforces the same rules independently, so a hidden button is a courtesy and never the thing that stops anyone. 6 new integration tests assert exactly that, hitting the endpoints directly as each role. **Upgrade safety**: a database created before permissions existed has users but no roles, and every endpoint used to be plain `[Authorize]` — so the first start of this version would have locked every existing user, the shop owner included, out of a system nobody was left able to grant access to. Startup therefore backfills the `Owner` role onto existing users, which preserves the access they already had rather than granting anything new. It is guarded on *no user holding any role at all* — exactly the upgrading-from-the-old-world state, which can never be true again once it has run. That guard is the point: a role-less user created later is someone an Owner has not yet approved, and must stay locked out rather than be quietly promoted by the next restart.

- Shop branding (`/dashboard/branding`): shop name, logo, contact details and theme colour, stored as ordinary `Setting` rows and applied by `useBranding()` in the dashboard shell — so the name, logo and colour follow the shop onto every screen rather than just the one that configured them. The colour is validated as a hex value before it is written to the `--primary`/`--primary-hover` CSS variables; an unvalidated value there would let a malformed setting break the styling of every page at once. The logo is a URL rather than an upload because `Setting.Value` caps at 4000 characters and there is no blob storage in this project yet.

### Known Gaps

- Profit and loss cannot be computed, and the new Orders & Collections report deliberately does not pretend otherwise. Three things are missing. (1) `ClothPrice` records both `CostPrice` and `SellingPrice`, but nothing links a cloth to an order: the New Order screen collects a cloth code, uses it to fill the unit price, then discards it — `CreateOrderItemInput` has no cloth-code field and neither `OrderItem` nor `FabricDetails` stores one, so the cloth actually used survives only as free text in `FabricType`. Persisting that link is the small change that would make cloth gross margin computable. (2) `Employee` has no wage or piece rate, so labour — usually the largest cost in a tailoring shop — cannot be costed at all, even though orders are already assigned to an employee. (3) There is no expenses entity anywhere in the domain (rent, power, machine maintenance, thread/buttons/lining). Until at least (1) and (2) exist, any "profit" figure would be revenue minus cloth alone and would overstate profit badly enough to be dangerous to act on.
- All 8 module frontends now exist (Customer, Measurement, Employee, Orders/Fabric Details, Billing, WhatsApp, Settings, Reports), but per 00_MASTER_SPEC.md § 15 Definition of Done none of them are fully "complete" — most have still only been exercised against the live database for a handful of manual paths, not their full CRUD surface.
- The WhatsApp send form can't associate a message with a specific order (see above) — every message sent from the UI today is customer-only, even though the backend and `WhatsAppMessageType.OrderStatusUpdate` both support an order association.
- ~~There is no user registration or admin user-management endpoint~~ — closed by the role-based user rights entry above: `/dashboard/users` creates users and assigns roles through the API. What remains is that permissions are fixed per role and not editable in the UI; a shop wanting a fifth role, or wanting `FrontDesk` to also see employees, needs a code change to `AppRoles`. That was the agreed trade for shipping this in one pass, and per-role permission editing is the natural next step.
- Roles are seeded at startup but users are not: a *fresh* database has no Owner until one is created directly against Identity, so the first login on a brand-new deployment still needs the same one-off bootstrap. Only an existing Owner can create the next user. (An *existing* database is handled — see the upgrade backfill in the user rights entry above.)
- Billing's credit/adjustment process for correcting a partially/fully paid invoice (02_DATABASE.md § 10.9) is not built — only voiding an invoice with zero payments is supported.
- WhatsApp's `MetaWhatsAppSender` has never sent a real message — no Meta Business/WhatsApp Business Account credentials have been available to test against.
- 01_ARCHITECTURE.md § 26's domain-event dispatch mechanism ("Now: ... dispatched in-process ... via the mediator") is described as already active but isn't actually implemented anywhere in this codebase — Billing's invoicing and WhatsApp's sending are both explicit commands as a result, not automatic reactions to an order status change, which is what the architecture doc's own example (order completion triggering billing/WhatsApp) describes.
