# Mathilens Tailoring ERP — instructions for Claude Code

An ERP for a tailoring shop. Two deployable applications in one repository:

| Path | What it is |
|---|---|
| `src/` | ASP.NET Core (.NET 10) API — Clean Architecture, logical CQRS, hand-rolled mediator, EF Core + PostgreSQL |
| `web/` | Next.js 16 / React 19 frontend, statically exported to Azure Static Web Apps |
| `tests/` | xUnit — `UnitTests` (domain, handlers, validators) and `IntegrationTests` (`WebApplicationFactory`) |
| `docs/` | Specifications, and the structured documentation platform described below |

`knowledge.md` is the architecture narrative — read it before making a substantial change; it explains
the mediator, the pipeline behaviors, the interceptors, the numbering schemes and the branch/static-export
constraints, with the reasoning behind each.

## House style

This codebase explains **why**, not what. Comments carry the decision and the alternative that was
rejected — often the bug that prompted it. Match that register: a comment that restates the code is
noise, and stripping an existing explanation destroys the most valuable thing in the file.

Other conventions that are deliberate, not accidental:

- **Dependencies are resisted.** The mediator, the ID ledger and the HTML generators are hand-written
  because a package would have been the larger change. Do not add one without saying why.
- **Domain entities have private setters and static factories.** Invariants live in the entity.
- **Handlers never validate, never log, never stamp audit fields** — pipeline behaviors and EF
  interceptors do. Adding a use case gets all three for free.
- **`Result`/`Error` for expected outcomes**, exceptions only for the genuinely exceptional.
- **`web/AGENTS.md` is generated by `next dev`.** Never hand-edit it; it will be overwritten.

## Verification

- Backend: `dotnet build MathilensERP.slnx` and `dotnet test MathilensERP.slnx`
- Frontend: `cd web && npx tsc --noEmit && npx eslint && npm run build`
- Documentation: `npm run docs:validate`

Never claim a test passed without running it.

## Documentation is part of the work

This repository maintains a structured, branch-aware documentation platform connecting
**FRS → Product Features → Source Code → Test Cases**, with change impact, historical evidence and
risk layered on top. It is not a separate chore: a source change that leaves the documentation
stale has left the task unfinished.

**The rules are in [.claude/documentation-rules.md](.claude/documentation-rules.md). Read them
before changing source code.** In short:

1. Structured JSON under `docs/data/**` is the source of truth. HTML is generated from it and is
   never edited by hand.
2. Never invent a requirement, a business rule, a dependency, a branch status, a test result or a
   defect. Where something is not known, say `NEEDS_REVIEW`.
3. Never modify an approved FRS entry to match what the code now does. Report the mismatch.
4. Facts and predictions are labelled differently: `CONFIRMED`, `INFERRED`, `PREDICTED`,
   `NEEDS_REVIEW`.
5. The repository is **public**. Never copy a credential into documentation — reference the key,
   never the value.

## The working tree may hold work that is not yours

Uncommitted changes are frequently present here. Do not commit, stash, reset, revert or reformat
anything you were not asked to change. Analysis must distinguish **committed** from **uncommitted**:
an untracked file describes one machine's working tree and is never branch history.
